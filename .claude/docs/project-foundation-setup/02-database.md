# Foundation 2 — Database

Part of the [project foundation setup](README.md). Read this to see how the database is built and verified, or to copy the approach into a new project. The *what* (tables, columns, rules) is in [database design](../database-design/database-design.md); this page is the *how it was set up*.

## What it gives you

- A Prisma schema ([prisma/schema.prisma](../../../prisma/schema.prisma)) with 40 tables and 20 enums, generated from the design doc.
- Three migrations in [prisma/migrations/](../../../prisma/migrations/), applied to the dev and the test database.
- Integration tests in [test/db/](../../../test/db/) that prove the database itself rejects bad data, so the rules cannot silently disappear.

## Local database

| Setting | Dev | Test |
| --- | --- | --- |
| URL | `postgresql://postgres:postgres@localhost:5433/book_my_ticket` | `postgresql://postgres:postgres@localhost:5433/book_my_ticket_test` |
| Host / port | `localhost` / `5433` | `localhost` / `5433` |
| User / password | `postgres` / `postgres` | `postgres` / `postgres` |

Port 5433 is the host side of the Docker mapping, so it does not clash with a Postgres installed on the machine. Start it with `pnpm infra:up`.

## Connect a database UI

**Quickest: Prisma Studio.** `pnpm prisma:studio`, then open http://localhost:5555. It needs no install and reads `DATABASE_URL` from `.env`.

**MySQL Workbench does not work.** It only supports MySQL/MariaDB. This project is PostgreSQL, so use one of these instead.

### pgAdmin (free, https://www.pgadmin.org)

1. Install pgAdmin 4 and start it.
2. Right-click **Servers** → **Register** → **Server…**
3. **General** tab: Name = `Book My Ticket (local)`.
4. **Connection** tab: Host name = `localhost`, Port = `5433`, Maintenance database = `book_my_ticket`, Username = `postgres`, Password = `postgres`. Tick *Save password*.
5. **Save**. Open **Databases → book_my_ticket → Schemas → public → Tables**. Right-click a table → **View/Edit Data → All Rows**.
6. For the test database, repeat with Maintenance database = `book_my_ticket_test`.

### DBeaver Community (https://dbeaver.io)

1. **Database → New Database Connection → PostgreSQL → Next**.
2. Host = `localhost`, Port = `5433`, Database = `book_my_ticket`, Username = `postgres`, Password = `postgres`.
3. Click **Test Connection** (let it download the driver the first time), then **Finish**.
4. Browse **book_my_ticket → Schemas → public → Tables**. Use **ER Diagram** on a table to see relations.

### Any other client (TablePlus, DataGrip, VS Code PostgreSQL extension)

Choose *PostgreSQL* and use the connection string from the table above. If you are asked for SSL, set it to *disable* (the local container has no TLS).

### Does it connect?

If the connection is refused, check the container is up: `docker compose ps` should list `postgres` as *healthy*. If the `book_my_ticket_test` database is missing, see [foundation 1](01-config-and-environment.md#test-environment).

## How the schema was built

1. **Prisma schema** written from the design doc. Conventions applied to every model:
   - ids: `String @id @default(uuid(7)) @db.Uuid` (time-ordered UUID v7, generated by Prisma)
   - timestamps: `@db.Timestamptz(3)`, `created_at` / `updated_at` on every mutable table
   - names: Prisma models are `PascalCase`; tables and columns are `snake_case` through `@@map` / `@map`
   - money is `Int` paise, rates are `Int` basis points
   - closed state sets are Prisma `enum`s, mapped to snake_case Postgres types
2. **Composite tenant foreign keys.** `theaters`, `screens`, `seat_categories` and `shows` have `@@unique([companyId, id])`. Their children (`screens`, `seats`, `shows`, `bookings`) reference `[companyId, id]`, so a child row can never point at a parent in another company. See `Screen`, `Seat`, `Show`, `Booking` in the schema.
3. **Three migrations**, in this order:

| Migration | Content |
| --- | --- |
| `20260101000000_extensions` | `citext`, `btree_gist`, `pg_trgm`. Written by hand, and dated before the others because `users.email` is `citext` and the extension must exist first |
| `..._core_schema` | Generated by `prisma migrate dev --create-only`: all tables, enums, FKs, plain indexes |
| `..._hand_written_constraints` | Everything Prisma cannot express: partial unique indexes, exclusion constraints, `CHECK`s, append-only triggers, covering/GIN indexes, invoice number sequence, `company_payable_balances` view |

Read the hand-written migration, not just `schema.prisma`: the rules that matter most live there.

## Rules enforced by the database

| Rule | Mechanism |
| --- | --- |
| A seat is sold once per show | partial unique index on `booking_seats (show_id, seat_id) WHERE status IN ('HELD','SOLD')` |
| One open checkout per customer per show | partial unique index on `bookings` |
| One open refund request per booking | partial unique index on `refund_requests` |
| One owner per company; role names unique | partial unique indexes on `company_staff`, `roles` (two, because NULLs are distinct) |
| Ledger recognised once per booking or membership | partial unique indexes on `ledger_entries` |
| No overlapping shows on a screen | `EXCLUDE USING gist` on `shows` (cancelled shows free the slot) |
| One active membership per customer per company | `EXCLUDE USING gist` on `customer_memberships` |
| Booking total adds up; refunded ≤ paid; payment kind matches its FK; ADJUSTMENT needs a memo | `CHECK` constraints |
| Ledger and audit rows are never edited or deleted; refunds never deleted | `forbid_mutation()` triggers |

## Keeping Prisma and the hand-written SQL in sync

`prisma migrate dev` compares the database with `schema.prisma` and would **drop** an index it does not know about. Partial indexes and exclusion constraints are ignored by that comparison, but two kinds are not:

- GIN indexes: declared in the schema with `@@index([genres], type: Gin, map: "...")`.
- The covering index `ledger_entries_balance_idx`: declared in the schema as a plain three-column index with the same `map:` name. The migration creates it with `INCLUDE (amount)`; Prisma sees no difference.

After editing the schema or a migration, run this and expect "No difference detected":

```bash
npx prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code
```

## How to change the database later

1. Edit `schema.prisma`.
2. `pnpm prisma:migrate` creates a migration (add `--create-only` to edit the SQL before it is applied, which you must do when the change involves a constraint Prisma cannot express).
3. Never edit an applied migration. Add a new one.
4. `pnpm prisma:migrate:test` to apply it to the test database, then `pnpm prisma:generate`.
5. New hand-written constraint? Add it to `test/db/catalog.e2e-spec.ts` and add a behaviour test in `test/db/constraints.e2e-spec.ts`.

## Tests that keep the constraints alive

Run with `pnpm test:e2e test/db`. They use the real test database (a mock would prove nothing) and refuse to run if `DATABASE_URL` does not contain `_test`.

| File | Proves |
| --- | --- |
| `constraints.e2e-spec.ts` | Cross-company screen/seat rejected. Overlapping show rejected, back-to-back allowed, cancelled show frees the slot. Overlapping membership rejected. Ledger UPDATE/DELETE blocked, duplicate recognition rejected, ADJUSTMENT needs a memo. 20 parallel claims on one seat give exactly one winner. An expired hold is released and re-claimed in one transaction, a live hold is never released |
| `catalog.e2e-spec.ts` | Every hand-written index, constraint, trigger, extension, function and view exists. Fails if a later migration drops or renames one |

These tests were checked to fail when the rule is removed: dropping the seat unique index makes the three seat-claim tests fail.

Test files share one database and do not truncate it. Each creates its own rows with random suffixes, so files can run in parallel.

## Things worth knowing

- **Trigger errors look like FK errors in Prisma.** The append-only trigger raises `restrict_violation`, which Prisma reports as "Foreign key constraint violated". Handle it where ledger writes happen; do not match on the message text.
- **`PrismaClient` must use the pg adapter** (`@prisma/adapter-pg`), as in `PrismaService` and the test helper. Prisma 7 has no built-in connection engine.
- **Raw SQL** is used only for the seat claim (`$queryRaw` with `ON CONFLICT ... DO NOTHING`). The reference implementation is `claimSeats` in `test/db/helpers.ts`; the real one moves into a repository file in the booking milestone.
- **Invoice numbers** come from `SELECT next_invoice_number()` (`INV-2026-000123`), called in the same transaction as the invoice insert.
- The Prisma client is generated into `src/generated` (gitignored). Run `pnpm prisma:generate` after every schema change and on a fresh checkout.

## Setting this up in a new project

1. Write the schema with the conventions above.
2. Add a hand-written `extensions` migration dated before the generated one.
3. `prisma migrate dev --create-only --name core_schema`, then another `--create-only` for the hand-written constraints.
4. Add `prisma:migrate:test` ([foundation 1](01-config-and-environment.md)).
5. Add the catalog test and one behaviour test per hand-written rule, with the test-database guard in the helper.
6. Run the `migrate diff` check above and keep it clean.
